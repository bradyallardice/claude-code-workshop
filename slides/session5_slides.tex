\begin{frame}{Subagents}
  \centering
  \vspace{2em}
  {\Large A focused agent spawned for a bounded job ---\\[0.3em]
  the right tool for the parallelizable, scoped work\\[0.3em]
  that already shows up in your pipeline.}

  \vspace{2em}
  Concrete patterns, then named teams.
\end{frame}

\begin{frame}{What a Subagent Is}
  \textbf{Claude Code can spawn another Claude Code instance inside your current session --- a subagent.}

  \vspace{0.6em}
  \begin{itemize}
    \item It has its own context window
    \item It gets a scoped task and a scoped tool set
    \item It returns a summary to your main conversation --- not its raw trace
  \end{itemize}

  \vspace{0.8em}
  \textbf{What that buys you:}
  \begin{enumerate}
    \item \textbf{Parallelism} --- run three searches at once instead of one after the other
    \item \textbf{Context hygiene} --- a big messy exploration stays out of your main context budget
  \end{enumerate}

  \vspace{0.5em}
  \begin{block}{Think of it as}
    Delegating a bounded sub-task to a focused colleague who returns a clean, structured answer --- so your main conversation stays on the high-level work.
  \end{block}
\end{frame}

\begin{frame}{Where Subagents Shine}
  \textbf{Reach for a subagent when the subtask is:}
  \begin{itemize}
    \item \textbf{Parallelizable} --- independent work that doesn't need to be sequenced
    \item \textbf{Bounded} --- clear inputs, clear outputs, no back-and-forth
    \item \textbf{Independently verifiable} --- you can check the result without reading the full trace
  \end{itemize}

  \vspace{0.7em}
  \textbf{Concrete research use cases:}
  \begin{itemize}
    \item \textbf{Multi-database literature searches} --- one agent per database, all running in parallel
    \item \textbf{Coding many documents} against a fixed rubric
    \item \textbf{Parallel robustness checks} across independent specifications
    \item \textbf{Running the same sanity-check} script over many datasets
    \item \textbf{Exploring a codebase} --- send a subagent to map out the files, keep the summary in your main context
  \end{itemize}
\end{frame}

\begin{frame}{How to Trigger a Subagent}
  \textbf{You don't have to set anything up --- just ask.}

  \vspace{0.6em}
  Claude Code ships with a general-purpose subagent built in. To spawn one, describe the work in plain English:
  \begin{itemize}
    \item \textit{``Send a subagent to map the directory structure''}
    \item \textit{``Use a subagent to find every place we set the random seed''}
  \end{itemize}

  \vspace{0.6em}
  \textbf{For parallelism, say so explicitly.}
  \begin{itemize}
    \item \textit{``Spawn three agents \textbf{in parallel} to search Zotero, Google Scholar, and Connected Papers''}
    \item ``In parallel'' / ``at the same time'' / ``concurrently'' all signal that the agents should run in one batch rather than sequentially
  \end{itemize}

  \vspace{0.6em}
  \begin{block}{No setup required}
    The general-purpose agent ships with Claude Code. Defining your own named agent (later this session) is for when you want to reuse a scoped role across many sessions.
  \end{block}
\end{frame}

\begin{frame}[fragile]{Using a Generic Subagent in Practice}
  \textbf{Worked example: one subagent, one bounded local task.}

  \vspace{0.3em}
  \textbf{Your prompt to Claude:}
  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
Spawn a subagent to read the slides for sessions 1-4
and return a deduplicated list of every unique terminal
command I'll need across the course.

Output as: command | what it does | first session
it appears in.
  \end{lstlisting}

  \vspace{0.2em}
  \textbf{What Claude does:}
  \begin{itemize}\small
    \item Spawns one general-purpose subagent and hands it the four \texttt{.tex} files
    \item The subagent does the reading, extraction, and dedup in its own context
    \item You get back the table; the slide text never lands in your main conversation
  \end{itemize}

  \vspace{0.2em}
\end{frame}

\begin{frame}{Using Subagents Well}
  \textbf{Three habits that make subagents pay off:}
  \begin{enumerate}
    \item \textbf{Brief them like a contractor.} Concrete deliverable, all the context they need up front --- they don't see your conversation history.
    \item \textbf{Ask for structured output} (bullet list, table, JSON). You'll be consuming the result; make it easy to read and verify.
    \item \textbf{Verify independently.} You get a summary, not the full trace. Spot-check the way you would a student's work.
  \end{enumerate}

  \vspace{0.8em}
  \begin{block}{The payoff}
    A literature sweep, robustness battery, or repo survey that would have taken an hour finishes in minutes --- and doesn't eat into your main conversation's context. That's what makes them worth reaching for.
  \end{block}
\end{frame}

\begin{frame}{What a Predefined Subagent Looks Like}
  \textbf{A small markdown file --- author it once, Claude spawns it many times.}

  \vspace{0.4em}
  \textbf{Where it lives:} \texttt{\textasciitilde/.claude/agents/<name>.md} (user-level) or \texttt{.claude/agents/<name>.md} (project-level).

  \vspace{0.5em}
  \textbf{What you specify} (metadata + body):
  \begin{itemize}
    \item \textbf{Identity} --- \texttt{name} and a one-line \texttt{description}. The description is what Claude reads to decide when to spawn this agent.
    \item \textbf{Tool allowlist} --- exactly which tools it can use (e.g.\ \texttt{Read} only, no \texttt{Bash}).
    \item \textbf{Model} --- Opus, Sonnet, or Haiku.
    \item \textbf{System prompt} --- the body of the file: role, disposition, expected output format.
  \end{itemize}

  \vspace{0.3em}
  \alert{\small Plain text --- metadata sits between two \texttt{-{}-{}-} lines at the top of the file; the system prompt is everything below.}
\end{frame}

\begin{frame}[fragile]{Building a Specialized Agent}
  \textbf{Worked example: turn ``audit my regression script'' into a reusable role.}

  \vspace{0.4em}
  \textbf{Walking through the four fields:}
  \begin{enumerate}\small
    \item \textbf{Name + description.} What it does, plus the one-line trigger Claude reads to decide when to spawn it.\\
    \emph{``Audit a regression script for silent issues.''}
    \item \textbf{Tool allowlist.} \texttt{Read}, \texttt{Grep}, \texttt{Glob} --- read-only. A critic that can fix code is no longer a critic.
    \item \textbf{Model.} \texttt{haiku} --- fast and cheap, fine for systematic pattern-matching.
    \item \textbf{System prompt.} Disposition + output contract: \emph{``You're a skeptical reviewer. Flag invalidating issues. Return: line, issue, why. Don't propose fixes.''}
  \end{enumerate}

  \vspace{0.3em}
  \textbf{Save as} \texttt{\textasciitilde/.claude/agents/spec-critic.md}.

  \vspace{0.3em}
  \textbf{Now in any session:}
  \begin{itemize}\small
    \item Claude auto-spawns it when a task matches the \texttt{description}
    \item Or invoke explicitly: \emph{``use \texttt{spec-critic} on \texttt{solution\_estimate.py}''}
    \item Role is enforced --- if it suggests a fix, it broke its own contract
  \end{itemize}

  \vspace{0.2em}
  \alert{\small Permissions still apply: tools the agent uses must be allowed in \texttt{.claude/settings.json}.}
\end{frame}

\begin{frame}{Why Define a Named Subagent at All?}
  \textbf{If skills are reusable, why not just spawn ad-hoc subagents that pick up the right skill?}

  \vspace{0.4em}
  \begin{block}{The framing}
    \textbf{Skills are knowledge. Subagents are roles.}\\
    A role bundles a disposition, a tool scope, and an invocation contract --- and then draws on skills to execute.
  \end{block}

  \vspace{0.3em}
  \textbf{Three things a role gives you that a skill can't:}
  \begin{enumerate}
    \item \textbf{Tool scope --- enforced.} A code-review subagent has read-only access, no bash. Skills are advisory; tool scopes aren't.
    \item \textbf{Identity, not advice.} The system prompt frames the whole disposition --- ``find problems, don't fix them.'' Subagents \textit{are} the disposition.
    \item \textbf{A stable invocation contract.} Delegate code review $\to$ get a structured critique. Ad-hoc means re-specifying the contract each time.
  \end{enumerate}

  \vspace{0.3em}
  \alert{\small Pre-define a subagent when the \textbf{role} is the reusable unit, not just the know-how.}
\end{frame}

\begin{frame}{Multi-Agent Workflows}
  \centering
  \vspace{2em}
  {\Large When one specialist isn't enough.\\[0.3em]
  Compose subagents into pipelines, fan-outs,\\[0.3em]
  and critic-builder loops.}

  \vspace{2em}
  Three patterns, one worked example.
\end{frame}

\begin{frame}{Three Composition Patterns}
  \textbf{Most multi-agent workflows are one of three shapes.}

  \vspace{0.7em}
  \begin{enumerate}
    \item \textbf{Fan-out / map-reduce.} N inputs, one specialist per input, merge at the end.\\
    \emph{Example:} code 50 interview transcripts against the same rubric --- one agent per transcript, then synthesize.

    \vspace{0.5em}
    \item \textbf{Pipeline.} Each stage's output is the next stage's input. Named and generic agents can mix.\\
    \emph{Example:} \texttt{spec-critic} flags issues $\to$ generic agent drafts fixes $\to$ \texttt{spec-critic} re-audits.

    \vspace{0.5em}
    \item \textbf{Critic-builder loop.} One agent produces, another reviews, the producer revises.\\
    \emph{Example:} a paragraph drafter $\leftrightarrow$ a paragraph-reviewer, two or three rounds.
  \end{enumerate}
\end{frame}

\begin{frame}[fragile]{A Pipeline in Practice}
  \textbf{Worked example: hardening a regression script in three stages.}

  \vspace{0.3em}
  \textbf{Your prompt to Claude:}
  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
Run this pipeline on solution_estimate.py:
  1. Use spec-critic to list every silent issue.
  2. Spawn a subagent to draft minimal-diff fixes
     for each issue.
  3. Re-run spec-critic on the patched script.
Return: original issues | proposed fixes | residual issues.
  \end{lstlisting}

  \vspace{0.3em}
  \textbf{What makes this work:}
  \begin{itemize}\small
    \item Each stage has a stable input/output contract --- so they compose
    \item Two \texttt{spec-critic} calls share a role but run in fresh contexts --- consistent without state
    \item Your main conversation only sees the final summary; intermediate traces stay isolated
  \end{itemize}

\end{frame}

\begin{frame}{One Agent or Many?}
  \textbf{Default to one agent. A team has to earn its keep.}

  \vspace{0.5em}
  \textbf{Stick with one agent when:}
  \begin{itemize}\small
    \item The task is bounded enough to fit one context window
    \item One disposition is enough --- no producer/critic split
    \item You're still exploring --- you don't yet know the right stages
    \item Orchestration overhead would dominate the actual work
  \end{itemize}

  \vspace{0.5em}
  \textbf{Reach for a team when:}
  \begin{itemize}\small
    \item The work has naturally distinct roles (writer + reviewer; auditor + fixer)
    \item Independent verification is the point --- a separate set of eyes
    \item You'll run the workflow many times --- the setup cost amortizes
    \item N independent inputs need the same treatment in parallel
  \end{itemize}

  \vspace{0.4em}
  \begin{block}{The test}
    Each extra agent is a stage that can drift. Add one only if it does something the previous one demonstrably can't.
  \end{block}
\end{frame}

\begin{frame}{Hooks}
  \centering
  \vspace{2em}
  {\Large Shell commands the harness runs automatically\\[0.3em]
  on events --- file writes, tool calls, session start.\\[0.3em]
  Enforcement that doesn't depend on Claude remembering.}

  \vspace{2em}
  Concept, one example, when to reach for one.
\end{frame}

\begin{frame}{What a Hook Is}
  \textbf{A hook is a shell command wired to a Claude Code event.} Configured in \texttt{.claude/settings.json}; run by the harness, not by Claude.

  \vspace{0.5em}
  \textbf{Common events:}
  \begin{itemize}\small
    \item \textbf{PreToolUse} --- before a tool runs (can block it)
    \item \textbf{PostToolUse} --- after a tool runs
    \item \textbf{SessionStart} --- at the start of a session
    \item \textbf{UserPromptSubmit} --- when you submit a prompt
    \item \textbf{Stop} --- when Claude finishes responding
  \end{itemize}

  \vspace{0.6em}
  \textbf{What this buys you:}
  \begin{itemize}\small
    \item \textbf{Enforcement, not advice.} The hook runs whether Claude remembers it or not.
    \item \textbf{Auditability.} Log every tool use, every edit, every Bash call.
    \item \textbf{Automation.} Format on save, refresh derived files, notify on completion.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Worked Example: A Research Audit Log}
  \textbf{Goal: every Bash command Claude runs gets logged with a timestamp --- automatically, every session.}

  \vspace{0.4em}
  \textbf{Add to \texttt{.claude/settings.json}:}
  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "echo \"$(date '+%F %T') $CLAUDE_TOOL_INPUT\" >> ~/research_log.txt"
      }]
    }]
  }
}
  \end{lstlisting}

  \vspace{0.3em}
  \textbf{What happens:} Before every \texttt{Bash} call, the harness runs the command above and appends a timestamped line to your research log. Claude can't bypass it --- the harness, not the model, runs hooks.
\end{frame}

\begin{frame}[fragile]{Installing a Pre-Built Hook: \texttt{claude-ignore}}
  \textbf{Many useful hooks already exist --- you don't have to write your own.}

  \vspace{0.3em}
  \textbf{What \texttt{claude-ignore} does:}
  \begin{itemize}\small
    \item A \texttt{PreToolUse} hook on \texttt{Read} that blocks files matched by a \texttt{.claudeignore} (gitignore-syntax patterns; comments and blank lines are ignored)
    \item Walks up from the current directory to root, merging every \texttt{.claudeignore} it finds --- different rules at different folder levels
    \item On a match, exits with code 2: hard block. Claude sees the failure and can't bypass it
    \item Use for \texttt{.env}, \texttt{*.secret}, raw data --- anything you don't want in the model's context
  \end{itemize}

  \vspace{0.3em}
  \textbf{Install + initialize:}
  \begin{lstlisting}[basicstyle=\ttfamily\small]
npm install -g claudeignore
cd ~/my_workspace/my_project && claude-ignore init
  \end{lstlisting}

  \vspace{0.2em}
  \texttt{init} creates a \texttt{.claudeignore} and wires the hook into \texttt{.claude/settings.json}.

  \vspace{0.2em}
  \alert{\small Source: \texttt{github.com/li-zhixin/claude-ignore}. Requires Node.js (npm).}
\end{frame}

\begin{frame}{Hook, Skill, or Agent?}
  \textbf{Three layers of automation, three different things.}

  \vspace{0.5em}
  \begin{block}{The framing}
    \textbf{Skills are knowledge. Subagents are roles. Hooks are guarantees.}
  \end{block}

  \vspace{0.5em}
  \textbf{Reach for a:}
  \begin{itemize}\small
    \item \textbf{Skill} when Claude needs to know \textit{how} to do X.
    \item \textbf{Subagent} when you want a delegated worker with a scoped role.
    \item \textbf{Hook} when something must happen regardless of what Claude remembers.
  \end{itemize}

  \vspace{0.5em}
  \alert{\small Hooks are the only one of the three the harness enforces. Skills are advice; subagents have agency; hooks are mechanical.}
\end{frame}

\begin{frame}{Capstone}
  \centering
  \vspace{1.2em}
  {\Large Read an unfamiliar paper,\\[0.35em]
  write a short literature review,\\[0.35em]
  replicate one published figure,\\[0.35em]
  run one small extension.}

  \vspace{1.2em}
  \begin{block}{The point}
    Use Claude Code as a research assistant, not as a vending machine. You learn the paper, direct the task, inspect the code, verify the output, and decide what the result means.
  \end{block}
\end{frame}

\begin{frame}{Assume You Have Not Read the Paper}
  \textbf{The first output is not code. It is orientation.}

  \vspace{0.5em}
  Before asking Claude to replicate anything, you should be able to answer:
  \begin{itemize}\small
    \item What is the paper's research question?
    \item What is the paper's core contribution?
    \item What treatment, attributes, and outcome are being analyzed?
    \item What does Figure 1 estimate, and why is it central?
    \item What does the assigned extension change or add?
    \item Which literatures does the paper claim to speak to?
  \end{itemize}

  \vspace{0.5em}
  \alert{\small Read the paper and my notes first. If Claude starts coding before you understand the target, stop it.}
\end{frame}

\begin{frame}[fragile]{Step 1: Clone, Teams, Branches}
  \textbf{Two-person teams, all working in the GitHub collaboration repo from Session 4.}

  \vspace{0.3em}
  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
git clone https://github.com/bradyallardice/github_collaboration_practice.git
cd github_collaboration_practice
git switch -c team-<n>/<your-name>-<strand>
  \end{lstlisting}

  \vspace{0.4em}
  \textbf{Assign two ownership lanes before touching files:}
  \begin{itemize}\small
    \item \textbf{Partner A: paper + literature lane} --- paper notes, Zotero search, literature review draft, claim checking
    \item \textbf{Partner B: data + analysis lane} --- data validation, Figure 1 script, extension script, output checks
    \item \textbf{Both: reciprocal review} --- each person reviews the other's PR before merging into the team branch
  \end{itemize}

  \vspace{0.4em}
  \alert{\small Everyone is doing the same capstone task. Branches keep identical work from colliding. Reviews keep partner specialization from becoming blind trust.}
\end{frame}

\begin{frame}{Step 2: Zotero, Not Local BibTeX}
  \textbf{The literature review uses a prebuilt Zotero library.}

  \vspace{0.5em}
  The workflow:
  \begin{enumerate}\small
    \item Import the provided BibTeX seed into Zotero.
    \item Confirm the Zotero MCP can find the papers.
    \item Remove the local import file from the project workspace.
    \item Ask Claude to search Zotero, not to mine a local \texttt{.bib} file.
  \end{enumerate}

  \vspace{0.6em}
  \begin{block}{Why}
    A local \texttt{.bib} file lets Claude pattern-match citations without understanding the literature. Zotero forces the workflow closer to the thing you would do in a real project: search, inspect, cite, and verify.
  \end{block}

  \vspace{0.3em}
  \alert{\small Instructor setup: the seed file should be a one-time import file, not a source Claude reads during drafting. If it must sit in the repo, block it with \texttt{.claudeignore} and the read guard.}
\end{frame}

\begin{frame}{Step 3: Write the Literature Review}
  \textbf{Use Claude for search and synthesis, but keep the claims accountable.}

  \vspace{0.5em}
  A useful first prompt:
  \begin{quote}\small
    Search the Zotero library for papers most relevant to this article's research question. Return a table with citation key, mechanism, empirical setting, and how it connects to the capstone paper. Do not write prose yet.
  \end{quote}

  \vspace{0.4em}
  Then:
  \begin{itemize}\small
    \item Open the most important papers or notes yourself.
    \item Decide which claims belong in a short review.
    \item Draft 2--3 paragraphs that position the capstone paper.
    \item Check that every citation supports the sentence attached to it.
  \end{itemize}
\end{frame}

\begin{frame}{Why Figure 1 Is Not a Skill}
  \textbf{Inside this capstone, reproducing Figure 1 happens once.}

  \vspace{0.6em}
