\begin{frame}[fragile]{\texttt{.claudeignore}: Works, Sometimes}
  The \texttt{.ignore} convention is everywhere in software:
  \begin{itemize}
    \item \texttt{.gitignore} (git), \texttt{.dockerignore} (Docker)
    \item \texttt{.npmignore} (npm), \texttt{.eslintignore}, \texttt{.prettierignore}
    \item \texttt{.gcloudignore}, \texttt{.terraformignore}, and many more
  \end{itemize}
  So \texttt{.claudeignore} is a commonly taught, perfectly reasonable extrapolation. You'll see it recommended across blogs, Reddit, and LLM-generated advice.

  \vspace{0.6em}
  What the testing actually shows:
  \begin{itemize}
    \item If you tell Claude \emph{explicitly} to respect it, it usually does.
    \item If you don't --- even after it reads \texttt{.claudeignore} and sees the pattern --- it will read the file anyway.
    \item There's no tool-level enforcement. It's a polite request that only lands when the model is listening.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{The Official Approach --- With Real Gaps}
  The docs point you at \texttt{permissions.deny} in \texttt{.claude/settings.json}:

  \vspace{0.3em}
  \begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
{
  "permissions": {
    "deny": [
      "Read(session_4/demo_output/tab_policy.*)",
      "Grep(session_4/demo_output/tab_policy.*)",
      "Glob(session_4/demo_output/tab_policy.*)"
    ]
  }
}
  \end{lstlisting}

  \vspace{0.2em}
  \textbf{The catch:} it blocks \texttt{Read}/\texttt{Grep}/\texttt{Glob}, not \texttt{Bash}. A \texttt{cat} in a shell command reads the file anyway.

  \vspace{0.3em}
  \alert{Safe assumption: if it's in the project, Claude can read it. Be deliberate.} Stronger mechanism coming with \alert{hooks}.
\end{frame}

\begin{frame}{First: What Is GitHub?}
  \begin{columns}[T]
    \column{0.66\textwidth}
    \textbf{GitHub is where code lives on the internet.}

    \vspace{0.4em}
    Every project is a \emph{repository} --- a folder with all its files plus the full history of every change.

    \vspace{0.6em}
    \textbf{Two copies of everything:}
    \begin{itemize}
      \item \textbf{Remote} --- the shared version on \texttt{github.com}
      \item \textbf{Local} --- the version on your machine
    \end{itemize}

    \column{0.30\textwidth}
    \centering
    \vspace{1em}
    \includegraphics[width=0.7\textwidth]{img/github.png}
  \end{columns}

  \vspace{0.8em}
  \begin{block}{The short version}
    GitHub hosts the \emph{shared} copy. You work on your \emph{local} copy. Git keeps them in sync.
  \end{block}
\end{frame}

\begin{frame}{The Vocabulary}
  \textbf{Five words that will keep coming back today:}

  \vspace{0.6em}
  \begin{itemize}
    \item \textbf{\texttt{clone}} --- make your first local copy of a remote repo
    \item \textbf{\texttt{pull}} --- fetch the latest changes \emph{from} the remote into your local copy
    \item \textbf{\texttt{push}} --- send your local changes \emph{to} the remote
    \item \textbf{branch} --- a parallel line of work inside the repo; changes on a branch don't affect anyone else until it's merged
    \item \textbf{pull request (PR)} --- a proposal to merge one branch into another, with a page on GitHub for review and discussion
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{The flow}
    \texttt{clone} once. \texttt{pull} before you start. Make a \textbf{branch}, commit, \texttt{push}, open a \textbf{PR}. Someone reviews and merges.
  \end{block}
\end{frame}

\begin{frame}{The Course Repo}
  \textbf{Our materials live in one GitHub repo.} Everything I push goes there; everything you pull comes from there.

  \vspace{0.6em}
  \textbf{Let's look at the page together.} Things to notice:
  \begin{itemize}
    \item The \textbf{file tree} --- \texttt{session\_1/}, \texttt{session\_2/}, \ldots, \texttt{session\_4/}
    \item The \textbf{README} --- what the repo is and how to use it
    \item The \textbf{commit history} --- every change I've made, with a message
    \item The \textbf{branches} --- \texttt{main} is the shared one; others are work-in-progress
  \end{itemize}

  \vspace{0.6em}
  \begin{alertblock}{Why this matters for what's next}
    The issue we hit last session lives exactly here: you and I were both editing files in the \emph{same} repo. To explain what went wrong, we need the picture of where things live.
  \end{alertblock}
\end{frame}

\begin{frame}{The Problem We Had}
  \textbf{Every session so far, someone has hit a merge conflict.}

  \vspace{0.6em}
  What we did about it:
  \begin{itemize}
    \item Deleted the local repo and recloned
    \item Asked Claude Code to resolve the conflict markers
    \item Copied work to the Desktop, wiped the directory, copied back
  \end{itemize}

  \vspace{0.8em}
  \textbf{That worked.} Everyone got unstuck. But it was a symptom fix.

  \vspace{0.8em}
  \begin{alertblock}{The Root Cause}
    You were editing files \emph{inside} the shared course repository. Every time I pushed new material, git had to reconcile your changes with mine. Conflicts were guaranteed by the structure, not by accident.
  \end{alertblock}
\end{frame}

\begin{frame}[fragile]{The Structural Fix}
  \textbf{New layout on my side:} each session is a self-contained folder.

  \vspace{0.3em}
  \begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
AIAgentsCourse/
  session_1/
  session_2/
  session_3/
  session_4/     <- today's materials live here
  ...
  \end{lstlisting}

  \vspace{0.5em}
  \textbf{New workflow on your side:} copy the session folder out of the repo into your own workspace. Work there. The shared repo stays read-only for you.

  \vspace{0.6em}
  \begin{block}{What this changes}
    I can push new material anytime without breaking anything in your workspace. You can edit, break, delete, and redo without worrying about the shared state. No more conflicts.
  \end{block}
\end{frame}

\begin{frame}[fragile]{The Three-Step Ritual}
  \textbf{Do this at the start of every session from now on:}

  \vspace{0.5em}
  \begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
# 1. Pull the latest course repo
cd ~/AIAgentsCourse && git pull

# 2. Copy today's session folder into your workspace
cp -r session_4/ ~/my_workspace/session_4/

# 3. Open your copy in VS Code and work there
cd ~/my_workspace/session_4 && code .
  \end{lstlisting}

  \vspace{0.5em}
  \textbf{We do it together now, live.} Five minutes. Everyone ends up in the same clean state before we move on.

  \vspace{0.5em}
  {\small If you had in-progress work inside the course repo, copy it into \texttt{\textasciitilde/my\_workspace/} too. I will help you sort out what to keep.}
\end{frame}

% ---- 2-prelude: What skills do, concretely ----------------------

\begin{frame}{What a Skill Actually Does}
  \textbf{Skills from my setup, and when each one fires:}

  \vspace{0.6em}
  \begin{itemize}
    \item \texttt{latex-regression-table} --- I ask for a results table. It writes a canonical CSV, renders a booktabs \texttt{.tex}, and compiles a PNG. One house style across the whole paper.

    \item \texttt{abstract-structure-audit} --- I paste a draft abstract. It checks whether the four standard moves (puzzle, approach, findings, contribution) are present, vague, or missing.

    \item \texttt{paragraph-structure-audit} --- I share a paragraph. It flags multiple claims per paragraph, smuggled assumptions, and weak transitions.

    \item \texttt{robustness-checks} --- I run a regression. It proposes a structured battery (alternative SEs, subsamples, IV, event study) and executes it.
  \end{itemize}

  \vspace{0.6em}
  \alert{Each one is a recurring workflow done the same way every time.}
\end{frame}

% ---- 2a: How a skill works --------------------------------------

\begin{frame}[fragile]{How a Skill Works}
  \textbf{A skill is a folder with a \texttt{SKILL.md} file in it.}

  \vspace{0.3em}
  \begin{columns}[T]
    \column{0.52\textwidth}
    \textbf{What you set up:}
    \begin{lstlisting}[basicstyle=\ttfamily\tiny]
~/.claude/skills/latex-tables/
  SKILL.md       <- required
  template.tex   <- optional
  examples/      <- optional
    \end{lstlisting}

    \textbf{\texttt{SKILL.md}} starts with frontmatter:
    \begin{lstlisting}[basicstyle=\ttfamily\tiny]
---
name: latex-tables
description: Use when generating a
  regression or summary-stats table.
---

# Instructions Claude follows
...
    \end{lstlisting}

    \column{0.46\textwidth}
    \textbf{How Claude uses it:}

    \vspace{0.3em}
    \begin{enumerate}\footnotesize
      \item At session start, Claude sees every skill's \texttt{name} + \texttt{description} --- nothing more
      \item \textbf{Two ways to invoke:} auto-call on a description match, or you call it yourself (\texttt{/latex-tables})
      \item The full \texttt{SKILL.md} body loads into context on demand
      \item Claude follows those instructions
    \end{enumerate}

    \vspace{0.2em}
    \begin{block}{\footnotesize The key idea}
      \footnotesize The \texttt{description} is the auto-call trigger. Write it so Claude can tell \emph{when} this skill applies.
    \end{block}
  \end{columns}
\end{frame}

% ---- 2b: The architecture ---------------------------------------

\begin{frame}{Before You Build a Skill, Ask Where It Belongs}
  \textbf{Three things look alike but are different tools:}

  \vspace{0.8em}
  \begin{enumerate}
    \item \textbf{Skills} --- reusable instruction bundles, loaded on demand
    \item \textbf{Project context} --- a CLAUDE.md inside your paper's directory
    \item \textbf{MCPs} --- connections to external systems
  \end{enumerate}

  \vspace{1em}
  \textbf{Most wishes of the form \emph{``I wish Claude knew X''} route to one of these three.}

  \vspace{0.4em}
  Knowing which one saves you from building a skill that should have been something else. It also tells you when a skill is \emph{too narrow} a tool for the job.
\end{frame}

\begin{frame}{The Routing Rule}
  \centering
  \vspace{1em}
  {\Large
    \textbf{Skills} $\rightarrow$ what's stable \emph{about you}\\[0.7em]
    \textbf{Projects} $\rightarrow$ what's stable \emph{within a paper}\\[0.7em]
    \textbf{MCPs} $\rightarrow$ what's \emph{live}
  }

  \vspace{1.8em}
  \begin{block}{}
    If X changes when the project changes, it's not a skill.\\[0.2em]
    If X is alive in an external system, it's not a skill either.
  \end{block}
\end{frame}

\begin{frame}{The Rule, Applied}
  \small
  \begin{tabular}{@{}p{6.8cm} p{5.8cm}@{}}
    \toprule
    \textbf{What you want Claude to know} & \textbf{Where it belongs} \\
    \midrule
    Your \LaTeX{} table conventions & Skill (stable about you) \\[0.3em]
    The variables \& specs of your current paper & Project context (within a paper) \\[0.3em]
    Your Zotero library & MCP (live external state) \\[0.3em]
    Your writing voice & Skill (stable about you) \\[0.3em]
    What your current paper argues & Project context (within a paper) \\
    \bottomrule
  \end{tabular}

  \vspace{0.8em}
  \begin{block}{Why this matters}
    Skills are a narrower tool than most people assume. That's a feature --- narrower tools are easier to use well.
  \end{block}
\end{frame}

% ---- 2c: Two clusters -------------------------------------------

\begin{frame}{Within Skills: Two Different Jobs}
  \begin{columns}[T]
    \column{0.48\textwidth}
    \textbf{Verification skills}

    \vspace{0.3em}
    Fire \emph{during or after} work to check it.

    \vspace{0.3em}
    \textit{Examples:} LLM-mistake checker, sanity-check validator, replication auditor.

    \vspace{0.3em}
    \textbf{Earn keep by:} catching real problems, even if used infrequently.

    \column{0.48\textwidth}
    \textbf{Production skills}

    \vspace{0.3em}
    Fire \emph{during the making} of something to shape it.

    \vspace{0.3em}
    \textit{Examples:} \LaTeX{} table skill, writing-style skill.

    \vspace{0.3em}
    \textbf{Earn keep by:} frequency --- every table, every document.
  \end{columns}

  \vspace{0.8em}
  \begin{alertblock}{Why the distinction matters}
    ``Is this worth it?'' has a different answer for each. Verification skills need to catch high-cost errors. Production skills need to fire often.
  \end{alertblock}
\end{frame}

% ---- 2d: The heuristic ------------------------------------------

\begin{frame}{The Heuristic}
  \centering
  \vspace{1em}
  {\Large Skills are for \textbf{conventions}\\[0.4em]
  you hold about how to do\\[0.4em]
  a thing correctly.}

  \vspace{1.2em}
  \small

  \vspace{0.8em}
  \normalsize

\end{frame}

% ---- 2f: The skills I don't use ---------------------------------

\begin{frame}{Finding Good Use Cases Is Hard}
  \textbf{Two skills I built but barely use:}

  \vspace{0.3em}
  \begin{itemize}
    \item \texttt{auto-commit} --- commits after every file edit
    \item \texttt{spec-validator} --- pre-estimation data and spec checks
  \end{itemize}

  \vspace{0.5em}
  \textbf{What they have in common:} each sounded useful in the abstract. Each was built on an idea of how research \emph{should} go. Each got replaced by a one-off prompt the first time I actually needed the job done.

  \vspace{0.4em}
  The specificity can also work against you --- a tightly scoped skill only fires when the exact shape of the task matches, and it's easy to build one whose niche never actually shows up.

  \vspace{0.5em}
  \begin{alertblock}{Strong recommendation}
    Do not go build five skills this weekend. You will not use most of them.\\[0.3em]
    Instead: \textbf{build one.} Try it on your current work. Tweak it where it fires wrong. Let it earn its place in your workflow. \emph{Then} add another.
  \end{alertblock}
\end{frame}

% ---- 2f2: How to build one that works ---------------------------

\begin{frame}{How to Build One That Works}
  \textbf{What separates a skill that fires right from one that sits unused:}

  \vspace{0.3em}
  \begin{itemize}
    \item \textbf{Write the description for the trigger, not the reader.} Claude decides whether to auto-call on the description alone. Name the task, the keywords, and what the skill does \emph{not} handle.

    \item \textbf{Keep it narrow.} One genre of table, one kind of audit, one workflow. Broad skills fire at the wrong moment, or never.

    \item \textbf{Encode your convention, not generic knowledge.} The \texttt{SKILL.md} should capture the judgment calls \emph{you} make. Claude already knows boilerplate.

    \item \textbf{Ship a reference example.} An \texttt{examples/} folder with a real working artifact gives Claude something concrete to pattern-match on.

    \item \textbf{Revise after the first real use.} Version one fires wrong somewhere. Fix the trigger or the instructions, retry.
  \end{itemize}
\end{frame}

\begin{frame}{Skills: The Arc}
  \begin{enumerate}
    \item Skills get abandoned when they're built on spec, not on pain
    \item Before building, \textbf{route:} stable-about-you, stable-within-a-paper, or live?
    \item Within skills, ask: \textbf{verification} or \textbf{production}?
    \item Skills are for \textbf{conventions} about how to do a thing correctly --- not for good intentions
    \item Skills are \textbf{empirical}: build, fail, refine
  \end{enumerate}

  \vspace{0.8em}
  \begin{block}{The durable takeaway}
    If what you want to codify is a convention about how \emph{you} do a thing correctly, and it doesn't live inside a paper or an external system --- then maybe it's a skill. Otherwise it's something else. And that's a feature.
  \end{block}
\end{frame}

% ---- 3a: Framing -------------------------------------------------

\begin{frame}{What an MCP Is}
  \textbf{MCP = Model Context Protocol.} An open standard for plugging external tools into Claude Code.

  \vspace{0.6em}
  \begin{itemize}
    \item Each MCP is a separate server.
    \item Claude Code speaks to it over a standard protocol.
    \item The server exposes \emph{tools} (like \texttt{zotero\_search}) that Claude Code can call.
  \end{itemize}

  \vspace{0.8em}
  \textbf{Without MCPs:} Claude Code reads and writes files in your project. That's it.\\[0.2em]
  \textbf{With MCPs:} it can query your Zotero library, open a GitHub PR, read a database, post to Slack --- anything someone has built a server for.

  \vspace{0.8em}
  \begin{block}{The framing}
    MCPs turn Claude Code from a tool that operates on your \emph{files} into a tool that operates on your \emph{workflow}.
  \end{block}
\end{frame}

% ---- Skill + MCP composition (bridge concept) -------------------

\begin{frame}{Where Skills and MCPs Compose}
  \textbf{The paragraph-structure skill is the first one you've seen that invokes an MCP.}

  \vspace{0.5em}
  \textbf{Alone:}
  \begin{itemize}
    \item \emph{Skill only:} ``This claim needs a citation. Figure one out.''
    \item \emph{MCP only:} ``Here's your Zotero library.'' But nothing knows when to search.
  \end{itemize}

  \vspace{0.5em}
  \textbf{Composed:}
  \begin{itemize}
    \item The skill knows \emph{when} a claim is mis-cited or uncited
    \item The MCP returns actual papers from your library that would support it
    \item The MCP constrains the skill to real papers --- no hallucinated citations
  \end{itemize}

  \vspace{0.4em}
  \begin{alertblock}{The pattern}
    A skill knows \emph{when} to act; an MCP provides \emph{live data}. Together, they do what neither can alone.
  \end{alertblock}
\end{frame}

\begin{frame}{The Two-Reason Rule}
  \textbf{Once you've routed something to an MCP, ask: which of two reasons?}

  \vspace{0.6em}
  \begin{enumerate}
    \item \textbf{Extend capability.} Let Claude Code do something it couldn't do at all.\\
    {\small Example: open a GitHub pull request. Query your Zotero library. Run a SQL query against your database.}

    \vspace{0.4em}
    \item \textbf{Reduce friction at a boundary.} Let it do something you \emph{could} already do, but where context-switching between tools kills the flow.\\
    {\small Example: inserting citations while drafting. You could look them up in Zotero and paste. But stopping to do that breaks writing flow.}
  \end{enumerate}

  \vspace{0.8em}
  \alert{Today I'm showing two specific MCPs I think are worth adopting. There are dozens more. The \emph{framework} is what transfers; the two cases are how you learn it.}

  \vspace{0.4em}
  Callback to the meta-lesson: MCPs are easy to accumulate. Ask what each one earns.
\end{frame}

% ---- 3b: Zotero --------------------------------------------------

\begin{frame}{The Friction Case: Zotero}
  \textbf{Drafting with citations normally looks like:}

  \vspace{0.3em}
  \begin{enumerate}
    \item Write a sentence that needs a citation
    \item Stop. Open Zotero. Search. Find the paper. Copy the cite key.
    \item Come back to the editor. Paste. Context-switch back into drafting.
    \item Repeat ten times per paragraph.
  \end{enumerate}

  \vspace{0.5em}
  \textbf{With the Zotero MCP:} ``Find me the Smith 2019 paper on voter ID, add it to refs.bib, and cite it here.'' Claude Code does the search, the BibTeX export, the \texttt{\textbackslash cite\{\}} insertion --- without you leaving the \texttt{.tex} file.

  \vspace{0.5em}
  \begin{block}{Why it earns its keep}
    \textbf{Reduce friction at a boundary.} You could already do all of this manually. The MCP just removes the tool-switch.
  \end{block}
\end{frame}

\begin{frame}{What the Zotero MCP Can Do}
  \textbf{The Zotero MCP exposes around two dozen tools. They fall into two buckets:}

  \vspace{0.5em}
  \begin{columns}[T]
    \column{0.48\textwidth}
    \textbf{Read from your library}
    \begin{itemize}\small
      \item \textbf{Search:} keyword, semantic (natural language), by tag, advanced filters
      \item \textbf{Browse:} collections, recent items, saved searches, RSS feeds
      \item \textbf{Pull metadata:} title, authors, abstract, BibTeX fields
      \item \textbf{Pull full text} of attached PDFs
      \item \textbf{Read} your existing notes and annotations
    \end{itemize}

    \column{0.48\textwidth}
    \textbf{Write back to your library}
    \begin{itemize}\small
      \item \textbf{Create notes} attached to items
      \item \textbf{Create annotations} on PDFs
      \item \textbf{Update tags} in batch across many items
      \item \textbf{Switch between libraries} (personal, group)
    \end{itemize}

    \vspace{0.6em}
    \begin{block}{\small What this unlocks}
      \small Claude can read the \emph{actual full text} of papers in your library --- not just the title --- so it can reason about what's \emph{in} the paper, not just whether the citation exists.
    \end{block}
  \end{columns}
\end{frame}

\begin{frame}[fragile]{Zotero MCP: Live Demo}
  \textbf{A single prompt:}

  \vspace{0.3em}
  \begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
Find three recent papers on voter ID laws from my
Zotero library, add them to refs.bib, and draft one
sentence citing each in methods.tex.
  \end{lstlisting}

  \vspace{0.4em}
  \textbf{What you'll see in the tool-call log:}
  \begin{enumerate}
    \item \texttt{zotero\_semantic\_search("voter ID laws")} --- finds candidates
    \item \texttt{zotero\_get\_item\_metadata(...)} --- pulls BibTeX fields for each
    \item \texttt{Write refs.bib} --- creates or appends to the bibliography
    \item \texttt{Edit methods.tex} --- inserts three sentences with \texttt{\textbackslash cite\{...\}}
  \end{enumerate}

  \vspace{0.5em}
  \alert{Watch the tool calls, not just the output. Seeing which tools fire tells you what the MCP actually does.}
\end{frame}

\begin{frame}[fragile]{Exercise: Mini Literature Review (15 min)}
  \textbf{You installed the Zotero MCP as Session 4 prework and pointed it at the shared group library \texttt{aina-articles} --- recent papers on economic voting.}

  \vspace{0.4em}
  \textbf{Your task.} Draft a \textbf{five-sentence literature review} on \emph{one} of:
  \begin{itemize}\small
    \item How economic conditions shape vote choice
    \item Whether voters punish incumbents for bad economies
    \item How economic voting differs across contexts (regimes, institutions, crises)
  \end{itemize}

  \vspace{0.3em}
  \textbf{Rules:}
  \begin{itemize}\small
    \item Every sentence cites at least one paper from \texttt{aina-articles}
    \item Only use cite keys that \emph{actually exist} in the library --- no hallucinations
    \item Claude does the searching, full-text reading, and drafting
  \end{itemize}

  \vspace{0.3em}
  \textbf{Prompt to start from:}
  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
Using only papers in my Zotero 'aina-articles' collection, find
5 relevant to [topic]. Pull the key claim from each full text,
then draft a 5-sentence lit review with \cite{} for each.
  \end{lstlisting}
\end{frame}

\begin{frame}{What to Watch For}
  \textbf{While the model works, watch the tool calls:}

  \vspace{0.4em}
  \begin{itemize}
    \item Did it run \texttt{zotero\_semantic\_search}, or skip search and guess?
    \item Did it actually pull \texttt{zotero\_get\_item\_fulltext}, or cite from titles alone?
    \item Do the claims in your sentences match what the papers actually say?
  \end{itemize}

  \vspace{0.6em}
  \textbf{After drafting, spot-check one citation.} Open the paper in Zotero. Does the sentence you wrote accurately represent what the paper argues?

  \vspace{0.6em}
  \begin{alertblock}{The real lesson}
    An MCP gives Claude \emph{access}. It does not give Claude \emph{judgment}. The failure mode to expect: a plausible sentence citing a paper that says something adjacent --- but not quite that. \textbf{You still read.}
  \end{alertblock}
\end{frame}

\begin{frame}{The Capability Case: GitHub}
  \textbf{GitHub MCP lets Claude Code do things you couldn't do by just editing files:}

  \vspace{0.6em}
  \begin{itemize}
    \item Open a pull request from a branch you've been working on
    \item Leave review comments on a coauthor's PR
    \item Create issues to track tasks you don't want to lose
    \item Push files to a remote repository
  \end{itemize}

  \vspace{0.8em}
  \textbf{Why now?} This morning's Git restructuring put you in a clean state. You are working in your own workspace. You understand the three states: local copy, pushed branch, shared main. The GitHub MCP is what closes the collaboration loop.

  \vspace{0.5em}
  \begin{block}{Why it earns its keep}
    \textbf{Extend capability.} ``Open a PR'' isn't something Claude Code can do without this. It's a genuine new capability, not a friction fix.
  \end{block}
\end{frame}

\begin{frame}{The Mental Model}
  \centering
  \vspace{0.3em}
  \begin{tikzpicture}[
    node distance=0.8cm and 1.2cm,
    box/.style={draw=anthropic, fill=lightgray, rounded corners, minimum width=3.3cm, minimum height=1cm, align=center, font=\small},
    arr/.style={->, thick, color=accent}
  ]
    \node[box] (local) {\textbf{Your local copy}\\ \texttt{\textasciitilde/my\_workspace/...}};
    \node[box, right=of local] (branch) {\textbf{Your pushed branch}\\ \texttt{origin/your-branch}};
    \node[box, right=of branch] (main) {\textbf{Shared main}\\ \texttt{origin/main}};

    \draw[arr] (local) -- node[above, font=\tiny] {push} (branch);
    \draw[arr] (branch) -- node[above, font=\tiny] {PR + merge} (main);
  \end{tikzpicture}

  \vspace{1em}
  \textbf{Branches + PRs are the collaboration mechanism.} The GitHub MCP is a \emph{helper} on top --- not a substitute.

  \vspace{0.5em}
  \begin{alertblock}{The discipline}
    Use \texttt{git} directly. Use the MCP when you're stuck or when the MCP genuinely saves steps. When things break, you need to understand what's actually happening --- and the MCP abstracts that away.
  \end{alertblock}
\end{frame}

\begin{frame}{MCPs: The Meta-Lesson, Again}
  \textbf{GitHub MCP is optional infrastructure. The underlying git workflow is not.}

  \vspace{0.8em}
  If you find yourself reaching for the MCP to fix a conflict --- sometimes that's the right move. But sometimes (like this morning's session-folder fix) it's papering over a structural problem.

  \vspace{0.8em}
  \begin{block}{Before adopting an MCP, ask}
    \begin{enumerate}
      \item Does this genuinely extend what I can do, or reduce real friction?
      \item Will I invoke it more than three times a month?
      \item Am I using it because it helps, or because it's new?
    \end{enumerate}
  \end{block}

  \vspace{0.5em}
  Most MCPs fail question 2. The two today pass all three --- \textit{for me}. Your answers may differ.
\end{frame}

\begin{frame}{Part 4: Subagents}
  \centering
  \vspace{2em}
  {\Large Know they exist.\\[0.3em]
  Know when to reach for them.\\[0.3em]
  Don't over-invest.}

  \vspace{2em}
  Ten minutes. No hands-on.
\end{frame}

\begin{frame}{What a Subagent Is}
  \textbf{Claude Code can spawn another Claude Code instance inside your current session --- a subagent.}

  \vspace{0.6em}
  \begin{itemize}
    \item It has its own context window
    \item It gets a scoped task and a scoped tool set
    \item It returns a summary (not its raw output) to your main conversation
  \end{itemize}

  \vspace{0.8em}
  \textbf{Two values:}
  \begin{enumerate}
    \item \textbf{Parallelism} --- run three searches at once instead of serially
    \item \textbf{Context hygiene} --- a big messy search doesn't pollute your main conversation
  \end{enumerate}

  \vspace{0.5em}
  \begin{block}{Think of it as}
    Delegating a bounded sub-task to a fresh colleague who doesn't see your notes --- and who reports back only the conclusion.
  \end{block}
\end{frame}

\begin{frame}{When They Shine --- and When They Don't}
  \textbf{Subagents help when subtasks are:}
  \begin{itemize}
    \item \textbf{Parallelizable} --- independent work that doesn't need to be sequenced
    \item \textbf{Bounded} --- clear inputs, clear outputs, no back-and-forth
    \item \textbf{Independently verifiable} --- you can check the result without needing the agent's full trace
  \end{itemize}

  \vspace{0.6em}
  \textbf{Research workflows that fit:}
  \begin{itemize}
    \item Multi-database literature searches (one agent per database)
    \item Coding many documents against a fixed rubric
    \item Parallel robustness checks on independent specifications
  \end{itemize}

  \vspace{0.6em}
  \textbf{Research workflows that don't fit:}
  \begin{itemize}
    \item Anything sequential and judgment-heavy --- most of your drafting, most of your analysis decisions
    \item Tasks that depend on your ongoing conversation context (subagents start cold)
  \end{itemize}
\end{frame}

\begin{frame}{The Honest Teaching}
  \textbf{Most research tasks do not have the shape that makes subagents worth it.}

  \vspace{0.6em}
  \begin{itemize}
    \item Most of what you do is sequential
    \item Most of your decisions depend on context the subagent won't see
    \item Most of your verification needs the full trace, not a summary
  \end{itemize}

  \vspace{0.8em}
  \textbf{If your workflow has parallel, independent, verifiable subtasks --- revisit this.} Otherwise, don't over-engineer.

  \vspace{0.8em}
  \begin{alertblock}{The meta-lesson, one more time}
    Subagents are genuinely useful for a specific shape of problem. They're also the shiniest thing in the toolkit right now. Asking \emph{``does my problem have that shape?''} is the whole game.
  \end{alertblock}
\end{frame}
